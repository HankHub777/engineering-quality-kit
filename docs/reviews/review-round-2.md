### N-2 — `.quality` symlinks let eqk write and delete outside the repo

Severity: high

**Commits**: `57252b7` fix(N-2): refuse to write or delete through symlinks in .quality

**Fix**: New `adoption.quality_dir_safe(root) -> (ok, reason)`. A missing `.quality` is safe. ### N-7 — Ctrl+C left tool processes running

Severity: medium

**Commits**: `eb25752` fix(N-7): stop the tool's process group when eqk is interrupted; `c77324d` test(N-7): make the interrupt test's cleanup type-check

**Fix**: In `run_check`, a nested `kill_group()` (`os.killpg(SIGKILL)`, falling back to `p.kill()`; non-POSIX: `p.kill()`) is shared by the timeout branch and a new `except BaseException:` branch. That branch kills the group, runs `communicate(timeout=5)` ignoring a second `TimeoutExpired`, then re-raises. No report is written.

**Before fix**:

```text
FAIL: test_sigint_kills_tool_process_group
AssertionError: False is not true : tool process kept running after Ctrl+C on eqk
```

Test setup: eqk started with `start_new_session=True` (it plays the terminal's foreground group), wait for the tool's pid file, `os.killpg(eqk_pgid, SIGINT)`, 15 s hard limit on eqk's exit, then the tool pid must die within 2 s. Cleanup kills both.

### R-1 — exit code after Ctrl+C is undocumented

**Problem**: after N-7, an interrupted eqk re-raises `KeyboardInterrupt`. Python then ends
itself with SIGINT: the parent sees `returncode -2`, and a shell sees `130`. The README exit-code
table (0–5) doesn't mention it. CI would see a signal exit, which is correct, but an agent or
script that maps every code might not handle it.

**Evidence** (same mechanism, measured):

```text
python on SIGINT -> -2
```

**Proposed fix**: docs only. Add a row "130 (signal) — interrupted; no report written" to the
README and SKILL.md tables. Optionally, `__main__` could catch `KeyboardInterrupt` and
`sys.exit(130)` explicitly (decision: keep Python's default signal exit, or normalise it).

### R-2 — misleading reason after a failed write

**Problem**: after N-3, a file whose write failed is in the manifest with the content hash.
`revert` keeps it with the reason "edited since apply; keeping it (use --force to remove)". Nobody
edited it; it is a partial write left by eqk. The user cannot re-`apply` ("already applied") and
must use `revert --force`, guided by a wrong reason.

`eqk/adoption.py` lines 208–211 (branch head):

```python
 208              digest = hashlib.sha256(a["content"].encode("utf-8")).hexdigest()
 209              with open(target, "x", encoding="utf-8", newline="\n") as fh:  # 'x' = fail if it exists
 210                  created.append({"path": a["path"], "sha256": digest})
 211                  fh.write(a["content"])
```

**Evidence** (write patched to fail on the first file):

```text
apply: disk full
re-apply: already applied (.quality/applied.json exists); run `eqk revert` first
revert: {'removed': [], 'kept': [{'path': '.quality/eqk.json', 'reason': 'edited since apply; keeping it (use --force to remove)'}], 'complete': False}
```

**Proposed fix**: record `"complete": false` in the manifest entry before writing, and flip it
to `true` after the write. `revert` then removes an entry still marked incomplete (eqk wrote
it, nobody could have edited it meaningfully), or at least uses the reason "partially written
by a failed apply". Older manifests without the key behave as today.

### R-4 — SKILL.md has no guidance for the new refusals

**Problem**: exit 4 now covers "`.quality` contains a symlink" (N-2) and "invalid
`eqk.json`/`applied.json`" (N-6). An agent following SKILL.md may try to "fix" the repo by
deleting the symlink or rewriting the file. That is exactly what should go to the user
(it may be an attack via a cloned repo).

**Proposed fix**: add a hard rule to SKILL.md: "If eqk refuses because `.quality` contains a
symlink or a config/manifest is invalid, stop and show the message to the user. Do not delete
or rewrite those files yourself."

### R-5 — `quality_dir_safe` walks the cache (not measured)

**Problem**: `os.walk` covers `.quality/cache/` (ruff and mypy caches can have thousands of
files) on every apply, revert and verify. Correct, but possibly slow on big repos. I did not
measure this.

**Proposed fix**: measure on a large repo first. If it matters, stop descending into a
directory once it is known not to be a symlink and only eqk writes into it. Or only walk
`evidence/` and `reports/` plus the top-level files, and check that `cache/` itself is not a
symlink. That second option weakens "any symlink inside", so it needs a decision.

### R-6 — killed child not reaped after N-8 gives up

**Problem**: when the second `communicate` times out, eqk closes the pipes and returns
without `p.wait()`. The direct child is already SIGKILLed, so it is a zombie until the `Popen`
object is garbage-collected (CPython reaps it then). No functional effect was observed; this
is noted for completeness.

**Proposed fix**: `p.wait(timeout=1)` (ignoring `TimeoutExpired`) after closing the pipes.
